The V220 trial did not test first-time clone or owner-state setup. It started
after V219 task one had completed and its candidate lesson had been saved. Its
question was narrower: can a new Codex chat with no V219 conversation follow
the prepared hub's ordinary routes, retrieve the saved candidate when the new
facts match, and use it without inheriting Shin's active state?

## Frozen input boundary

post-task-one checkpoint, plus a new task request and reservation facts. The
completed V219 task-two capsule, answer, expected result, validation record,
and later V219 commits were absent from its refs and object database. The
launch prompt did not name the saved note or prescribe the expected judgment.

The isolated trial repository and raw Codex application log were deliberately
not published. The commit identifiers above are stable local evidence

The reservation facts already said that a ledger entry was not readiness, the
tool might remain on loan, physical shelf confirmation was required before
`ready for pickup`, and no pickup hours, promised date, or notification
permission were supplied. Those operational conclusions are not attributed
exclusively to saved memory.

What V220 confirms about reuse is the executed process and framing: the fresh
chat retrieved the saved candidate, compared its trigger and limits to the new
facts, selected it as advisory rather than authority, applied recorded /
unverified / actionable separation, and used `UNKNOWN` when transition
evidence was missing.

Because there was no no-memory control and the input was already explicit,
the saved note's added quality, causal necessity, error prevention, explanation
reduction, or token effect remains `UNKNOWN`.

## Relationship to the V219 worked example

Exact output reproduction was not required and did not occur. The fresh result
split unresolved return and pending shelf confirmation into two intermediate
labels, while the V219 worked example used one combined intermediate label and

The fresh capsule referenced the note directly in the same committed
repository instead of copying the worked example's separate selected-note

a non-blocking implementation difference, not an exact-answer claim.

## Public claim boundary

procedure and worked example as a bounded candidate. It does not establish:

- first-time setup ease for a real third party;
- general or repeated fresh-chat reliability;
- real-workflow correctness or error reduction;
- token, model-usage, time, or cost reduction;
- general quality improvement; or
- public adoption or star growth.

The public candidate therefore remains an explained manual path, not a new
installer, capsule generator, selector, service, or automated memory product.

Publishing the README entry, quickstarts, worked example, V219 record, and
this bounded V220 projection makes the local-clone personal-hub route
