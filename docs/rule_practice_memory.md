# ルールを使った経験を、次の利用へ戻す

版付き台帳の対象は既存の **FN125（継続時の証拠選択）一つ**です。普段は
[現行カード](rule_practice/fn125.md)のルール・適用条件・例外・版・未解決の注意点だけを
読みます。判断の理由が必要になった時だけ、カードから実践記録と元の証拠へ降ります。
全履歴の通読、Companion、別モデル、サーバーは不要です。

<a id="closure-selection"></a>
## 通常の完了・中断前の軽い選別

普通の開発依頼、`♻️`、予定した中断・圧縮・引き継ぎの前に、Codexが今回の作業から一度選別する。
まず作業中に確認できた選択理由、実行結果、証拠だけを見る。新しい差分がなければそこで終了し、
この手順のために全履歴を読み直したり、全ルールを移行したりしない。

- 読んだだけで判断に使わなかった記録、同条件・同結果で情報が増えない経験は追加しない。
- 候補、手順、適用強度、タイミング、停止判断が変わった場合は、何が変わり、どの証拠が支え、
  次のどんな条件で役立つかを確認する。参照の事実だけから影響や防げた失敗を推測しない。
- 新しい適用条件、反例、予想外の結果、負担、後日結果は候補とする。結果が未知なら成功・失敗を付けず、
  分かっている部分、未確認部分、再評価条件を残す。保存件数や「学習した」印象を目的にしない。
- 同じ作業の再開・再報告では、関連する実行IDと既存の観測だけを検索する。同じ情報なら追加なし。
  差分がある場合だけ旧記録を残して追記し、台帳では同じ`execution_id`と`supersedes`を使う。

保存価値がある場合は、次の既存の場所を使う。

| 対象 | 保存と次回取得 |
| --- | --- |
| FN125の版に対応する実使用 | 下記の既存台帳へ差分を追記し、カードを再生成・検査する。効果未確認は未評価のまま残す |
| 特定ルールへの帰属が不明な開発経験・後日結果 | その作業の既存`validation/`等の実行記録へ、安定した実行ID、条件、変わった判断、結果、証拠、未確認と再訪条件を追記。必要なら既存の条件別索引から最小のリンクを付ける。既存記録がなければ一件だけ作る。無理にFN125へ帰属させない |
| 合成試用・接続確認 | 既存の検証記録に合成・試用と明記する。実使用の台帳や成功数へ混ぜない |

原ログの重複転記は避け、元の記録と固定sourceを参照する。重要な未解決の注意点だけを関連する入口へ戻す。
新しい実行記録を作った場合は、今回参照した既存の作業記録か条件別索引から、その記録へ進むリンクを
一つ確認してから保存完了とする。新記録から原記録への逆向きリンクだけでは、元の入口から取得できない。
再開時にも関連する保存済み記録の未保存部分・未接続の入口を確認し、必要な接続だけを現在の許可内で補う。
この補完は同じ作業の後始末であり、新しい経験や追加件数として登録しない。
追記とルール改訂は別の操作であり、追記から新しい権限・Canon昇格・実行許可は生じない。
既存ルール自体の変更が必要なら、経験と候補理由を保存した上で、現在の変更権限を別に確認する。
Shinの承認によるV13内の必要な追記・索引接続は現在の作業範囲の後始末として行い、毎回判断を戻さない。
他の所有者のworkspaceではその人の設定・書込範囲を使い、Shinの承認を転用しない。

保存後は実ファイルを読み戻し、参照先と差分を確認する。台帳を変えた場合は下記の`--check --base`も行う。
書込み・検査・索引接続が失敗した場合は「保存済み」にせず、既存のhandoff／現在の作業報告へ
未保存または部分保存の内容、実行ID、対象path、エラー、どの条件なら再開できるかを残す。
別の場所へ無断で書込範囲を広げず、再開時には既に書けた部分を先に照合して重複を避ける。
全ての書込みが不能なら会話のhandoffで渡す。予告なくプロセスが終了してこの手順を実行できない場合の
保存は保証しない。

普通の報告には一行だけ加える。

- `実践記憶：1件追記。後日結果を使って重複修復を除外したため。`
- `実践記憶：追加なし。既存の条件・結果と重複するため。`
- `実践記憶：保存未完了。結果は未確認で、書込再開条件をhandoffへ残した。`

追加不要なら専用ファイル・「追加なし」履歴は作らない。記憶の保存・再生成・検査・移送それ自体を
新しい経験として再帰的に保存しない。ただし、その処理で実際の新しい欠陥を発見した場合は、通常の
不具合記録として一度扱い、保存した事実を再び経験として増殖させない。
これはAGENTSに従うAIの選別・実行手順であり、常駐処理や終了イベントの自動フックではない。
下記のコード検査はID・形式・参照・旧履歴・カード一致を検査するが、保存価値、意味上の重複、
因果効果、所有者の許可や証拠が実例かどうかを自動判定しない。

## 通常の使い方

1. 現在の作業許可と AGENTS.md を確認し、証拠選択が必要なら現行カードを読む。
   注意点が今回の条件に関係すれば、その記録と証拠まで読む。重要な不一致を
   解消できなければ、元のルールに従って該当操作を止める。
2. 許可された実作業でルールを使う。単なる参照、接続確認、模擬テストとは区別する。
3. 作業を閉じる時に上の選別を行い、保存する差分がある場合だけ既存の実行記録を参照して
   [同じ下層ファイル](../evidence/rule_practice/fn125.json)へ追記する。
   利用者に同じ内容の再入力や定型操作を求めない。記録のために仕事を作らない。
4. 下記の評価基準で維持・修正候補・条件別分岐候補・休止候補、または未評価を記す。
   カードを再生成し、変更差分と検証を確認する。候補だけでルールを書き換えない。

```console
python3 scripts/rule_practice.py --write --base origin/main
python3 scripts/rule_practice.py --check --base origin/main
```

引数なしなら短いカードを標準出力へ出します。`--write` はカード一枚だけを更新します。
`--check` は固定した元ルールの内容、証拠ファイル、重複・評価条件、カードの一致を
検証します。`--base` は取得済みの比較元にある版と実践記録が変更・削除されていないかを
検証します。新しい記録とカードは同じ変更としてレビュー・保存します。
スクリプトは評価の妥当性や承認の有無を自動判定せず、記録内の文章を実行しません。
検証失敗時はカードを最新と主張せず、原因を調べます。
同じ実行でIDと`supersedes`だけを変えた同内容の追記は検査で拒否します。意味が同じ別表現や
別IDで偽装した同一作業までは検出できません。`--write`は一時ファイルからカードを置換し、
置換前の失敗で既存カードを壊さないようにします。台帳とカードを一括保存するtransactionではありません。

## 最小の実践記憶

既存の `validation/` 実行記録を一次証拠にし、JSON は短い索引として使います。
記すのは、使った版、安定した実行 ID、条件、判断・行動への影響、観測結果、
手戻り・負担、未確認事項、証拠への参照、判断理由と再評価条件です。
実行ログをコピーせず、必要な差分を一度だけ書きます。関係する新観測がなく、
単に読んだだけなら記録は不要です。未観測の実使用は残し、成功扱いしません。

- `kind: applied` は実作業で識別可能なルールの働きがあった場合。
  `reference` / `connection` は実践の母数から除外する。
- `result: observed` は結果を観測したという意味。成功・効果確認とは同義ではない。
  結果が不明なら `unknown` と理由を残す。テストデータは `tests/` のメモリ内だけに置く。
- `execution_id` は repository + 実際の task/run + 同一の操作単位で固定する。
  再記録・read-back・訂正に新しい実行 ID を振らない。既存 ID を検索してから追記する。
  同じ実行の追記は `supersedes` で直前の記録を指す。版を跨いでも実行数は一件。
  別 ID に偽装された同一実行を自動認識する機能はないため、証拠の同一性もレビューする。
- 反例は `issue: counterexample`、適用条件との不一致は `condition_mismatch`。
  修正・分岐・休止候補も未解決の注意点として最上層へ必ず出す。
  古い版の反例も、版変更や後続の維持判断だけでは消さない。
- 解消は、観測済み実作業の追記に `resolves: [以前の記録ID]`、
  `resolution_reason` と証拠を書く。未知の結果や単なる接続確認では閉じられない。
  人間の判断が必要な変更を伴う場合は、その現在の承認まで証拠から辿れることを確認する。

## 経験をどう評価するか

回数・新しさ・文章の説得力だけで判断しない。条件と結果のつながり、証拠の確かさ、
実際に変わった判断・行動、反例、負担、Aspire と再開可能性への影響を一緒に見る。
無変更も正常な成果であり、改訂しなかった条件と根拠を残す。

| 判断 | 必要な根拠 | 次の利用への戻し方 |
| --- | --- | --- |
| `maintain` 維持 | 適用条件が合い、識別可能な利用と結果を観測し、当該条件で維持する理由を説明できる。反例がないだけでは足りない | 版を維持し、成立した条件・限界・再評価条件を保存。一般的有効性へ拡大しない |
| `revise` 修正候補 | 反例や不要な負担と、現行ルールのどこが結果に関係したかを証拠で示せる | 注意点を上層へ返し、最小の修正案と反証条件を検討 |
| `split` 条件別分岐候補 | 条件差によって必要な判断が異なる。成功側・失敗側または不足する比較が識別できる | 適用範囲を明示し、不足比較は未確認のまま残す |
| `pause` 休止候補 | 現在の適用では保護条件を損なう、または重大な不一致が未解決 | 元の停止規則を適用し、再開条件を上層へ返す。記録自体は新たな権限ではない |
| `unassessed` 未評価 | 単なる参照、結果不明、証拠不足、未確認の因果 | 成功・維持の確認に数えず、何を観測すれば評価できるかを残す |

同じ実行を複数回保存しても独立した経験になりません。10回・20回という閾値は
使いません。一つの重大な反例で見直し得る一方、多数の参照だけでは改訂も昇格もしません。
評価基準自体に不具合が出たら、その実例を既存の実行記録に残してこの節の
限定修正を検討します。評価基準を評価する管理階層や自動ループは追加しません。

## 版・ライフサイクル・権限

`fn125-v1` は既存 Canon の内容を固定 commit / path / SHA-256 に結び付けた識別子です。
実践記憶で最初に束ねた版であり、FN125 の過去の改訂履歴を「初版」に戻す意味ではありません。
元のルールと過去の判断を上書きしません。改訂する時は、承認されたルール変更を
Git に保存してから新しい版とその変更理由・承認証拠を追加し、`current_version` と
カードを切り替えます。旧内容へ戻す場合も新しい版として記録します。

現在の許可内で行える証拠参照の補修・実践の追記・注意点の更新は AI が引き受けます。
目的、権限、保護条件、公開範囲を変える改訂は Shin（fork ではその Decision Owner）の
現在の判断が必要です。`change_scope: human_judgment` として、具体的な候補と
影響まで準備してから判断を戻します。過去の承認を新しい変更へ流用しません。

[Field Note lifecycle](field_note_lifecycle.md) と AGENTS.md §7 の昇格条件をそのまま使います。
この台帳は `Canon-promoted` 等とは別の観測・評価の軸です。Companion の
`CANDIDATE / REUSED / PROMOTABLE` 台帳や Compound Evidence Meter に自動加算しません。
将来の ♻️ は必要なカードと根拠を参照できますが、選択範囲・実行権限・自動継続を
この接続から増やしてはいけません。

## 過去の選択に後日観測をつなぐとき（必要時だけ）

通常のカード読みには追加しません。後日の結果が今の選択に関係する時だけ、
既存の `validation/` 実行記録へ戻ります。
[一件の接続例：♻️ Run 3 → 後日の修正・main反映](../validation/delayed_outcome_case_001.md)を
使い、次の最小範囲で記録します。

1. 元の実行 ID と固定 commit / path を再利用し、当時の目的・選択理由・完了を残す。
   候補は少数に区切り、適切な証拠がなければ未確認で止める。
2. 原文を変更せず、別の観測を追記・参照する。「当時分かっていたこと」「後から
   分かったこと」「現在への含意」を分け、発生・記録・確認時刻を分かる範囲で区別する。
   commit 時刻から実行時刻を推測せず、不明には理由を付ける。
3. 同じ実行の後日確認に新しい実行 ID を発行しない。同じ観測 ID の訂正は、旧観測を
   残して `supersedes` で繋ぐ。未観測を失敗とせず、後の結果で当時の合理性を断定しない。
4. ルールの版との対応が証拠で明確なら既存の実践台帳へ戻す。不明なら例のように
   `rule_id: null` のまま次の選択への含意を残し、FN125 の利用や成功に加算しない。
5. 重要な未解決事項が現在の適用に関係する場合だけ、要点と下層参照を既存の入口へ返す。
   ルール帰属が明確ならその現行カード、帰属不明で次の選択に関係するなら current pair の
   Current Restart Point と必要な注意点を使う。今回は配置不一致の解消を確認したため、通常カードを増やさない。
   効果未確認の問いと再訪条件は下層に残し、実作業や新しい証拠が現れた時だけ再訪する。

この接続は新しい指示・実行権限・自動巡回を作りません。記録や配達の成功だけで
効果改善を確認済みとせず、目的・権限・保護条件の変更は既存の判断経路を守ります。

## 取得と判断を確認した範囲

[5観点の検証記録](../validation/memory_five_patterns/report.md)は、維持・条件差・未解決の失敗・
後日結果・改訂と休止について、必要時の深掘りと不要時の非取得を分けて記録しています。
初回9試用とPR #165の一件再利用、読み過ぎ2件に対する一度ずつの再確認です。
残る全文読み・合成データ境界の報告漏れも保存し、全件成功や一般的効果は主張しません。
変更はAGENTS.mdの歴史照会経路の境界だけで、FN125本文・版・カード・実践台帳は維持しました。
この観点分類を新しい保存形式や、普段の必読項目にはしません。

m03の合成データ限定の報告漏れには、[原回答を残した訂正と一回の取得・報告確認](../validation/fn125_scope_correction.md)を接続しました。
該当する検証ケースの比較にはこの限定を伴わせ、実業務での効果へ読み替えません。
